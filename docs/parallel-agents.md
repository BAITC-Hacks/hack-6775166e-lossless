# Параллельная работа в Codex

Задача выбрана: «Аким на 5 часов». Общие правила и проверочные случаи приведены в [сводке ТЗ](task-requirements.md), исходные DOCX — в `task/`. Движок и веб-интерфейс, уже находящиеся в `main`, — тестовая версия, не актуальная реализация для сдачи. Команды setup и запуска финальной версии фиксируйте только после её интеграции и проверки.

Для обычного Git worktree есть скрипт (запускать из основного checkout):

```bash
./scripts/agent-worktree create integrations
./scripts/agent-worktree create memory
./scripts/agent-worktree list
./scripts/agent-worktree run integrations -- pwd
./scripts/agent-worktree remove integrations
```

Worktree расположены в `.agent-worktrees/<имя>`, ветки — `agent/<имя>`. После удаления чистого worktree ветка сохраняется; повторный `create` подключит её. Скрипт откажется удалять worktree с незакоммиченными или неотслеживаемыми файлами. Игнорируемые `.agent-runtime` и `.venv` удаляются вместе с worktree, поэтому нужные логи из `.agent-runtime/logs` сохраните до `remove`.

`run` выделяет отдельные `PORT` (диапазон 20000–39999), `TMPDIR`, `XDG_CACHE_HOME`, `AGENT_DATA_DIR`, `AGENT_LOG_DIR` и `.venv` для каждого worktree. Команда выполняется в его каталоге, вывод пишется в `.agent-runtime/logs`. Для интерактивной сессии можно выполнить `eval "$(./scripts/agent-worktree env integrations)"` и перейти в соответствующий worktree. При появлении Python-зависимостей создавайте venv командой `python3 -m venv .venv` внутри каждого worktree. Приложение должно читать `PORT` и `AGENT_DATA_DIR`, если использует порт и локальное хранилище.

Скрипт копирует отслеживаемый `AGENTS.md` при создании worktree. После изменения инструкций обновите копию вручную, если worktree уже существует. Сведения для эксперта должны также находиться в README.

## Запуск

1. Саша как интегратор использует [сводку ТЗ](task-requirements.md) и согласует интерфейсы с Егором. Официальный старт уже прошёл; теперь приоритет — рабочий сквозной сценарий до 17:00 по времени Астаны.
2. Координирующий агент создаёт в Codex отдельную задачу для каждой независимой части в этом проекте. Каждая задача стартует в собственном **Worktree** от общей актуальной ветки. Агент выполняет назначенный пункт, проверяет его и сообщает commit, изменённые файлы и команду проверки.
3. Саша отвечает за интеграцию в основном checkout: собирает изменения, запускает сквозную проверку буквально по README и отвечает за итоговую отправку в командный репозиторий.

Пример задания агенту после распределения пунктов ТЗ:

> Реализуй пункт [точная цитата/ссылка на ТЗ] в своём worktree. Твоя зона файлов: [пути]. Согласуй интерфейс с интегратором до правки общих файлов. Проверь результат командой [команда] и сообщи наблюдаемый результат, commit и ограничения. Не изменяй чужие зоны и не отправляй итоговую версию вместо интегратора.

## Сборка результата

- В каждом worktree используй собственную ветку `agent/<часть>` (скрипт создаёт её автоматически), сделай содержательный commit и передай интегратору имя ветки или commit. Не используй одну ветку в двух worktree одновременно.
- Общие файлы, прежде всего `README.md`, манифесты зависимостей и конфигурацию запуска, меняет интегратор после согласования интерфейсов. Если агенту нужно их изменить, сначала сообщи интегратору конкретную правку.
- Интегратор переносит готовые commits в основную ветку, разрешает конфликты, проверяет матрицу ТЗ и чистый запуск. Перед часовым контрольным сроком отправляет реальный результат и сверяет удалённый commit.
- `AGENTS.md` отслеживается Git и содержит актуальные правила задачи для команды. `.worktreeinclude` добавляет его в новые управляемые Codex worktree, а скрипт выше копирует файл в обычный worktree при создании. Сведения для эксперта также внеси в сдаваемый README.

## Разделение работы для этой задачи

| Часть | Ответственный | Результат | Проверка до интеграции |
| --- | --- | --- | --- |
| Данные и расчёт | Саша | Исходные районы, каталог M1–M14, валидатор, лаги, синергии и Score | База 52,55768; пример за 95; ошибки бюджета, повторов, конфликтов и районов |
| Интерфейс | Егор | Выбор пяти мер, района, просмотр бюджета, дельт и итогового Score | Два разных допустимых сценария дают разные показатели и понятный результат |
| AI-объяснение | Егор | Текст о сильных сторонах, рисках и компромиссах по рассчитанным данным | AI не изменяет числовой результат и не сообщает невычисленные числа |
| Интеграция и сдача | Саша | README, переменные окружения, демонстрация и проверка чистого запуска | Эксперт повторяет основной сценарий без устных пояснений |

Егор и Саша согласуют интерфейсы и пути файлов до параллельных правок. Основной сценарий прототипа проверен локально; перед сдачей Саша проверяет финальную версию вместе с изменениями Егора. Видимые поля формы и порядок отправки записаны в [документе сдачи](submission.md): Саша должен завершить push, сверить удалённый commit и заполнить форму до 18:00, поскольку после дедлайна push блокируется.

### Фактическое разделение после старта

Созданы отдельные ветки/worktree `agent/engine`, `agent/interface`, `agent/explanation`, `agent/visualization`, `agent/benchmark-data`, `agent/optimizer`. Задача исследования graph patching и `gentle_precision` работает в своём управляемом Codex worktree. Основной checkout `main` — единственная точка интеграции и отправки. Точные границы файлов и API записаны в [контракте](contracts.md).

Worktree изолирует файлы и ветку, но сам по себе не ускоряет разработку: параллельно запускаются только независимые задачи с согласованным интерфейсом. Интегратор переносит проверенные коммиты по одному и повторяет затронутый сценарий. Benchmark и внешние данные не меняют стартовые значения пяти районов в приложении.

Приоритет до первого полного прогона: валидатор и Score → выбор пяти мер через UI → объяснение из рассчитанных фактов → запуск по README. Визуализация и подсказка оптимизатора добавляются, только если основной сценарий остаётся проверяемым. Точный перебор служит эталоном: исследовательский метод допускается в продукт после сравнения с ним по Score, времени и ограничениям на одинаковых входах.


## Платные API и приёмка NVIDIA-прогонов

Команда сообщила о лимите NVIDIA API **$100** на аккаунте Егора и OpenAI API **по $50** на аккаунтах каждого из двух участников. Это распределение доступа, а не подтверждение текущего остатка. Владелец аккаунта проверяет цену и остаток перед запуском. Ключи не публикуют в issue, логах, commit или артефактах.

Критичные модельные прогоны, влияющие на выбор решения или выполнение обязательного пункта ТЗ, направляй на NVIDIA при наличии подходящей модели и бюджета. Ответственный агент создаёт issue в этом репозитории с упоминанием Егора `@neverexz` и по возможности назначает его assignee. До ответа Егора агент готовит локальные входные данные, команду и критерии приёмки. Используй такую структуру issue:

```md
## Цель
Пункт ТЗ / проверяемая гипотеза: ...
Почему нужен NVIDIA API: ...

## Задание Егору
Исполнитель: @neverexz
Модель и версия: ...
Входные данные и расположение (без секретов): ...
Точная команда / запрос и параметры: ...
Число прогонов и верхний предел расходов: ...
Срок: ...

## Результат
Формат вывода, путь к артефактам и необходимые метаданные: ...
Ожидаемый наблюдаемый результат и критерии успеха: ...

## Приёмка агентом
Ответственный: ...
Команда проверки результата: ...
Команда запуска затронутого сценария / тестов: ...
```

После прогона агент сверяет фактическую модель, параметры и артефакты с issue, запускает проверку и основной сценарий по README, фиксирует команды и наблюдаемый результат в issue. Ошибки в коде исправляет и повторяет затронутую проверку; issue закрывает только после приёмки. Отсутствие прогона или отказ запуска фиксирует как блокер, не отмечает пункт ТЗ выполненным. Итоговый README должен позволять эксперту проверить ключевой сценарий без доступа к личному NVIDIA или OpenAI аккаунту участников.
