# Параллельная работа в Codex

Задача выбрана: «Аким на 5 часов». Общие правила и проверочные случаи приведены в [сводке ТЗ](task-requirements.md), исходные DOCX — в `task/`. Движок и веб-интерфейс, уже находящиеся в `main`, — тестовая версия, не актуальная реализация для сдачи. Команды setup и запуска финальной версии фиксируйте только после её интеграции и проверки.

Сначала узнай путь нужного worktree на компьютере владельца:

```bash
git worktree list
./scripts/agent-worktree list
```

Обычные worktree расположены в `.agent-worktrees/<имя>`, ветки — `agent/<имя>`. Некоторые задачи работают в управляемых Codex worktree вне этого каталога: путь смотри в задаче агента. Не создавай заново ветку, уже занятую другим агентом, и не запускай двух агентов в одном каталоге. Скрипт откажется удалять worktree с незакоммиченными или неотслеживаемыми файлами.

Для **обычного worktree, созданного этим скриптом**, команда `./scripts/agent-worktree run engine -- python3 -m unittest discover -s tests -v` запускает проверку в его каталоге. `run` выделяет отдельные `PORT` (диапазон 20000–39999), `TMPDIR`, `XDG_CACHE_HOME`, `AGENT_DATA_DIR`, `AGENT_LOG_DIR` и `.venv`; вывод пишется в `.agent-runtime/logs`. Для управляемого Codex worktree используй его фактический путь из задачи, а не предполагай, что он находится в `.agent-worktrees/`. Приложение должно читать `PORT` и `AGENT_DATA_DIR`, если использует порт и локальное хранилище.

Скрипт копирует отслеживаемый `AGENTS.md` при создании worktree. Уже запущенные Codex-задачи и worktree **не получают новые инструкции автоматически**. Егор и Саша должны передать своим агентам таблицу владельцев из `AGENTS.md` и актуальный [контракт](contracts.md) перед следующей правкой; для старого worktree обновить файлы из `main` без потери незавершённой работы. Сведения для эксперта также должны находиться в README.

## Запуск

1. Саша и Егор подтверждают [контракт API](contracts.md) и владельцев файлов до зависимых правок. Приоритет — рабочий сквозной сценарий до 17:00 по времени Астаны; тестовая версия `main` не является финальной приёмкой.
2. Каждый Codex-агент работает только в закреплённой за ним ветке и worktree, меняет свою зону файлов и передаёт владельцу commit, список файлов, выполненные проверки и блокеры. Чужой файл или форму ответа API нельзя менять без согласования с его владельцем.
3. Саша отвечает за интеграцию в основном checkout: собирает изменения, запускает сквозную проверку буквально по README и отвечает за итоговую отправку в командный репозиторий.

Короткие сообщения для уже запущенных агентов:

> **Агент Саши:** твоя ветка — одна из `agent/engine`, `agent/benchmark-data`, `agent/optimizer`. Найди точную зону своей ветки в `docs/contracts.md`; не меняй `web/`, `src/explanation.py`, `src/server.py` и общие файлы. Если нужен иной API, передай Саше предложение для согласования с Егором. Сообщи SHA commit, файлы, проверку и блокеры. В `main` не пушь.

> **Агент Егора:** твоя ветка — одна из `agent/interface`, `agent/visualization`, `agent/explanation`. Найди точную зону своей ветки в `docs/contracts.md`; не меняй расчёт, `src/server.py`, README и общие файлы. Интерфейс и модель используют рассчитанный Score, не вычисляют его заново. При изменении API передай Егору предложение для согласования с Сашей. Сообщи SHA commit, файлы, проверку и блокеры. В `main` не пушь.

> **Агент интеграции Саши:** работай в основном checkout на `main`. Принимай только готовые commits из зон `docs/contracts.md`, проверяй diff каждого агента и объединяй по одному. После каждого объединения запускай затронутые тесты; после объединения движка, интерфейса и объяснения проверь реальный сквозной сценарий по README. README и `.env.example` обновляй по фактической версии. Перед push проверь чистый статус и сообщи Саше точный SHA удалённого commit и оставшиеся блокеры. Не выдавай тестовый прототип за финальную версию.

## Сборка результата

- В каждом worktree используй только уже назначенную ветку `agent/<часть>`, сделай содержательный commit и передай владельцу SHA. Не используй одну ветку в двух worktree одновременно.
- Общие файлы, прежде всего `README.md`, манифесты зависимостей и конфигурацию запуска, меняет интегратор после согласования интерфейсов. Если агенту нужно их изменить, сначала сообщи интегратору конкретную правку.
- Саша переносит готовые commits в `main` по одному после просмотра diff и проверок, разрешает конфликты, проверяет матрицу ТЗ и чистый запуск. Перед часовым контрольным сроком отправляет реальный результат и сверяет удалённый commit.
- `AGENTS.md` отслеживается Git и содержит актуальные правила задачи для команды. `.worktreeinclude` добавляет его в новые управляемые Codex worktree, а скрипт выше копирует файл в обычный worktree при создании. Сведения для эксперта также внеси в сдаваемый README.

### Фактическое разделение после старта

По сообщению команды, отдельные ветки/worktree уже созданы. **Саша** принимает `agent/engine`, `agent/benchmark-data`, `agent/optimizer` и исследовательские предложения по graph patching и `gentle_precision`; **Егор** принимает `agent/interface`, `agent/visualization`, `agent/explanation`. Это владельцы результата: каждый отдельный агент остаётся в своей конкретной ветке и зоне файлов из [контракта](contracts.md). Основной checkout `main` — точка интеграции Саши и единственная ветка финальной отправки.

Worktree изолирует файлы и ветку, но сам по себе не ускоряет разработку: параллельно запускаются только независимые задачи с согласованным интерфейсом. Саша переносит проверенные коммиты по одному и повторяет затронутый сценарий. Перед каждым объединением он проверяет, что diff не вышел за зону ветки, запускает `git diff --check` и затронутые тесты. После объединения движка, интерфейса и объяснения он проверяет через реальный сервер пример за 95 и 56.54307, невалидный набор без Score, источник AI-объяснения и браузерный путь. Benchmark и внешние данные не меняют стартовые значения пяти районов в приложении.

Приоритет до первого полного прогона: валидатор и Score → выбор пяти мер через UI → объяснение из рассчитанных фактов → запуск по README. Визуализация и подсказка оптимизатора добавляются, только если основной сценарий остаётся проверяемым. Точный перебор служит эталоном: исследовательский метод допускается в продукт после сравнения с ним по Score, времени и ограничениям на одинаковых входах.


## Платные API и приёмка NVIDIA-прогонов

Команда сообщила о лимите NVIDIA API **$100** на аккаунте Егора и OpenAI API **по $50** на аккаунтах каждого из двух участников. Это распределение доступа, а не подтверждение текущего остатка. Владелец аккаунта проверяет цену и остаток перед запуском. Ключи не публикуют в issue, логах, commit или артефактах.

Критичные модельные прогоны, влияющие на выбор решения или выполнение обязательного пункта ТЗ, направляй на NVIDIA при наличии подходящей модели и бюджета. Ответственный агент создаёт issue в этом репозитории с упоминанием Егора `@neverexz` и по возможности назначает его assignee. До ответа Егора агент готовит локальные входные данные, команду и критерии приёмки. Используй такую структуру issue:

```md
## Цель
Пункт ТЗ / проверяемая гипотеза: ...
Почему нужен NVIDIA API: ...

## Задание Егору
Исполнитель: @neverexz
Модель и версия: ...
Входные данные и расположение (без секретов): ...
Точная команда / запрос и параметры: ...
Число прогонов и верхний предел расходов: ...
Срок: ...

## Результат
Формат вывода, путь к артефактам и необходимые метаданные: ...
Ожидаемый наблюдаемый результат и критерии успеха: ...

## Приёмка агентом
Ответственный: ...
Команда проверки результата: ...
Команда запуска затронутого сценария / тестов: ...
```

После прогона агент сверяет фактическую модель, параметры и артефакты с issue, запускает проверку и основной сценарий по README, фиксирует команды и наблюдаемый результат в issue. Ошибки в коде исправляет и повторяет затронутую проверку; issue закрывает только после приёмки. Отсутствие прогона или отказ запуска фиксирует как блокер, не отмечает пункт ТЗ выполненным. Итоговый README должен позволять эксперту проверить ключевой сценарий без доступа к личному NVIDIA или OpenAI аккаунту участников.
