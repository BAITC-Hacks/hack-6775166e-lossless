Общие файлы меняет Саша как интегратор. Если агенту нужен чужой файл или изменение API, он передаёт точное предложение владельцу; Саша фиксирует согласованное изменение здесь, после чего зависимые ветки обновляются. Визуализация монтируется в `#district-chart` через `window.renderDistrictCharts(container, result)`. 3D-схема монтируется в отдельный контейнер через `window.createCityScene(container, {onSelect})` и возвращает объект с `update({districts, selected, affected, resultDistricts, mode, decisions, measures})`, `pickDistrict(clientX, clientY)`, `setDropPreview(name)`, `setInitiativePreview({measureId, district}|null)` и `destroy()`. `pickDistrict` возвращает название района под экранными координатами указателя либо `null`, учитывая поворот, масштаб и прокрутку; `setDropPreview` принимает название района или `null` для снятия подсветки. `districts` — словарь исходных районов каталога, `resultDistricts` — словарь районов из валидного ответа симулятора или `null`; `mode` — `baseline` либо `result`. `decisions` — текущий пакет `{measure_id, district}`, `measures` — каталог M1–M14; до расчёта сцена называет их проектом пакета, после валидного расчёта — решениями в модели. При переключении «Было» интерфейс скрывает модели мер, чтобы исходное состояние не показывало будущие объекты. `onSelect(name)` передаёт название выбранного района. `affected` — массив названий районов, на которые распространяется подсвеченная мера; он показывает охват, а не рассчитанный Score. `setInitiativePreview` показывает только временную модель выбранной меры и не меняет пакет. Интерфейс проверяет цель перетаскивания до добавления меры, но сервер повторяет все проверки при расчёте. Схема условная, не географическая карта. Интерфейс, графики, оптимизатор и LLM не пересчитывают числовой Score и не подменяют результат `simulate()`.

Компактная сцена одной меры монтируется через `window.createInitiativeDiorama(container)` и возвращает `update({measure, district, mode})` и `destroy()`. `measure` — объект каталога или `null`; `mode` равен `preview`, `plan` либо `result`. Она повторяет готовый выбор и не вычисляет эффекты или Score. Без Canvas текстовая подпись остаётся доступной.

## Вход и выход

`GET /api/catalog` возвращает JSON с `districts`, `measures`, `base_score`. Все пользователи получают одни и те же исходные данные и бюджет 100.

`POST /api/simulate` принимает:

```json
{"decisions":[{"measure_id":"M7","district":"Нура"},{"measure_id":"M8","district":"Нура"},{"measure_id":"M10","district":"Нура"},{"measure_id":"M12","district":null},{"measure_id":"M5","district":"Сарыарка"}]}
```

В полной заявке должно быть ровно пять разных мер. Для городской меры `district` равен `null`; для районной указан один из пяти районов. Пример выше должен дать стоимость `95` и Score `56.54307`. Сервер вызывает `simulate(decisions)` и возвращает JSON с `valid`, `errors`, `cost`, `remaining_budget`, `base_score`. Для валидного набора дополнительно возвращает `score`, `districts`, `deltas`, `contributions`, `applied_synergies`, `explanation`. Для невалидного набора `score` отсутствует, а `errors` содержит причины. Счёт и дельты вычисляет только детерминированный модуль.

Числовой результат сохраняет полную точность внутри модели; интерфейс округляет Score до двух знаков. AI получает уже рассчитанные данные и не меняет числовые поля. Если модель недоступна, сервер явно сообщает об этом и предоставляет проверяемое объяснение из вычисленных фактов, не называя его ответом модели.

Объяснение формируют `explain(result, *, diagnostics=False)` и `explain_comparison(current, proposed, removed, added, *, diagnostics=False)` из `src/explanation.py`. Модель выбирает только ID заранее рассчитанных фактов; строгая проверка ответа исключает неизвестные ID, лишние разделы и произвольные числовые результаты. OpenAI использует Responses API со строгой JSON-схемой, NVIDIA — совместимый Chat Completions API через необязательный SDK из `requirements-model.txt`.

Настройки `NVIDIA_API_KEY`, `NVIDIA_MODEL`, `OPENAI_API_KEY`, `OPENAI_MODEL` читаются из `.env` текущего клона; значения процесса имеют приоритет, в том числе пустые. При двух полностью настроенных парах приложение выбирает NVIDIA. Явный выбор OpenAI для приложения: `NVIDIA_API_KEY= NVIDIA_MODEL= python3 src/server.py`. Таймаут сетевой операции OpenAI — 20 секунд с учётом первого запроса по новой JSON-схеме, NVIDIA — 45 секунд; повторных вызовов и переключения провайдера после ошибки нет. Интерфейс ожидает запрос расчёта и объяснения до 75 секунд.

Успешное объяснение имеет поля `text`, `source: "model"`, `provider`, `model`; резервное — `text`, `source: "computed_facts"`, `reason: "model_not_configured"` либо `"model_unavailable"`. При `diagnostics=True` диагностический скрипт получает также безопасные `error_code`, `error_type`, `http_status` и сведения о выбранной модели, если они доступны. HTTP API использует обычный режим без диагностических деталей. Интерфейс отображает источник объяснения и не выдаёт резервный текст за модельный.

`python3 scripts/check-model.py --provider openai --check-config` проверяет наличие настроек без сетевого вызова. `python3 scripts/check-model.py --provider openai --scenario both` выполняет два реальных запроса: объяснение контрольного плана и объяснение одной замены. `NVIDIA_API_KEY= NVIDIA_MODEL= python3 scripts/check-model-advice.py` отдельно проверяет совет по приоритету одним живым OpenAI-запросом. Скрипты не выводят ключи; подробный протокол — в `docs/model-run-issue.md`.

`GET /api/optimize` ищет максимум Score для исходных данных задачи и возвращает валидный расчёт вместе с `decisions`, метаданными `optimization` и `explanation`. Сервер повторно проверяет найденный набор через `simulate()`. Оптимальный план по заданной модели: M2/город + M3/Нура + M8/Нура + M9/Нура + M14/город, стоимость `98`, Score `57.236735`. Интерфейс отображает сравнение районов и объяснение оптимального плана; ручной пакет меняется только после выбора пользователя. Сам поиск на текущем хосте занимает около 4 секунд и кэшируется в процессе сервера; объяснение формируется для каждого запроса отдельно.

`POST /api/recommend-change` принимает тот же `{"decisions":[...]}`, что и `/api/simulate`, и для корректного набора ищет лучшую допустимую замену не более одного решения. Возвращает `current` и `proposed` как полные результаты `simulate()`, `decisions` предложенного плана, `removed`, `added`, `score_delta`, `cost_delta` и `explanation`. Для невалидного набора возвращает HTTP 400 с причинами без Score. Предложенный набор повторно проверяется симулятором; модель получает оба готовых расчёта, но не меняет их. Интерфейс применяет замену только после нажатия пользователя. Для контрольного пакета замена M5/Сарыарка на M3/Нура даёт стоимость `100`, Score `57.20556` и прирост `0.66249`; это отдельный режим от глобального оптимума.

`POST /api/advice` принимает `{"decisions":[...],"question":"Почему замена ухудшает Сарыарку?"}` после составления полного плана. Сервер валидирует те же пять решений и независимо считает три варианта: `current` — исходный план, `one_change` — лучшая допустимая замена одного решения по Score, `optimum` — глобальный максимум Score заданной модели. Ответ содержит `valid: true`, `options: [{id, label, result, decisions, tradeoff}]` и `advice: {text, source, selected_option}`; `result` каждого варианта — полный проверенный результат `simulate()`. При настроенном API-ключе LLM интерпретирует вопрос и возвращает только ID варианта для обсуждения и ID проверенных фактов; сервер собирает итоговый текст без свободного текста модели. `selected_option` содержит один из перечисленных ID либо `none`, если такого выбора нет, и не управляет расчётом. Вопрос длиной от 1 до 500 символов влияет на выделение фактов, но не на входные решения, допустимые варианты и числа. Для распознанного явного запрета ухудшать указанный район сервер дополнительно отклоняет выбор модели, если районный Score выбранного варианта ниже текущего. На контрольном наборе одна замена повышает Score `56.54307 → 57.20556`, но районный балл Сарыарки снижается на `1.2125`, а Нуры растёт на `2.02`. Человек сам выбирает, оставить ли свой план. При отсутствии модели `source: computed_facts` обозначает объяснение из вычисленных фактов и `selected_option: none`; `source: model` возможен только после действительного ответа API-модели. При резервном ответе советника после сбоя провайдера допустимы только безопасные `error_code` и `http_status` из фиксированного набора; текст ошибки, тело ответа и ключ не возвращаются. Для невалидного набора сервер возвращает причины без Score.

## Контроль интеграции

1. Начальный Score: `52.55768`.
2. M7/Нура + M8/Нура + M10/Нура + M12/город + M5/Сарыарка: стоимость `95`, Score `56.54307`.
3. Невалидный набор возвращает причины без `score`.
4. Перестановка пяти решений не меняет результат.
5. Одна замена контрольного плана: стоимость `100`, Score `57.20556`; глобальный оптимум: стоимость `98`, Score `57.236735`.
6. Объяснения контрольного плана, одной замены и глобального оптимума видны в интерфейсе вместе с источником. 3D-схема использует те же исходные и рассчитанные районы.
7. «Показать проверочный сценарий» проходит обычную серверную валидацию. Перетаскивание и диалог выбора мер формируют одинаковые решения.
8. `/api/advice` возвращает те же три числовых результата независимо от вопроса; без модели источник `computed_facts` и `selected_option: none`.
9. README проверен по чистому запуску до финального push.

Интегратор переносит законченные изменения в `main` после проверки команды и тестов. Отдельный benchmark расширяет уверенность в оптимизаторе, но не подменяет контрольные случаи из датасета задачи.

Готовность ветки к передаче означает: владелец сообщил SHA commit, изменённые файлы, команды и наблюдаемые результаты проверок, а также ограничения. Саша сначала проверяет diff на выход за зону ветки, затем объединяет по одной законченной ветке и повторяет затронутый сценарий. Работа исследовательских агентов, включая graph patching и `gentle_precision`, не попадает в продукт автоматически: Саша принимает её только после сравнения с обязательным сценарием и воспроизводимым эталоном.
