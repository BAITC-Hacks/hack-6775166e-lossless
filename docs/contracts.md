# Контракты параллельной разработки

Состояние на 23 сентября: рабочий контракт для интеграции. Исходные числа и правила задают `task/` и `docs/task-requirements.md`. Текущий код в `main` команда считает тестовой версией, не финальной реализацией. Если контракт противоречит ТЗ, Саша и Егор согласуют исправление до правки зависимых частей.

Общие файлы меняет Саша как интегратор. Если агенту нужен чужой файл или изменение API, он передаёт точное предложение владельцу; Саша фиксирует согласованное изменение здесь, после чего зависимые ветки обновляются. Визуализация монтируется в `#district-chart` через `window.renderDistrictCharts(container, result)`. Новая 3D-схема монтируется в отдельный контейнер через `window.createCityScene(container, {onSelect})` и возвращает объект с `update({districts, selected, affected, resultDistricts, mode})` и `destroy()`. `districts` — словарь исходных районов каталога, `resultDistricts` — словарь районов из валидного ответа симулятора или `null`; `mode` — `baseline` либо `result`. `onSelect(name)` передаёт название выбранного района. `affected` — массив названий районов, на которые распространяется подсвеченная мера; он показывает охват, а не рассчитанный Score. Схема условная, не географическая карта. Интерфейс, графики, оптимизатор и LLM не пересчитывают числовой Score и не подменяют результат `simulate()`.

## Вход и выход

`GET /api/catalog` возвращает JSON с `districts`, `measures`, `base_score`. Все пользователи получают одни и те же исходные данные и бюджет 100.

`POST /api/simulate` принимает:

```json
{"decisions":[{"measure_id":"M7","district":"Нура"},{"measure_id":"M8","district":"Нура"},{"measure_id":"M10","district":"Нура"},{"measure_id":"M12","district":null},{"measure_id":"M5","district":"Сарыарка"}]}
```

В полной заявке должно быть ровно пять разных мер. Для городской меры `district` равен `null`; для районной указан один из пяти районов. Пример выше должен дать стоимость `95` и Score `56.54307`. Сервер вызывает `simulate(decisions)` и возвращает JSON с `valid`, `errors`, `cost`, `remaining_budget`, `base_score`. Для валидного набора дополнительно возвращает `score`, `districts`, `deltas`, `contributions`, `applied_synergies`, `explanation`. Для невалидного набора `score` отсутствует, а `errors` содержит причины. Счёт и дельты вычисляет только детерминированный модуль.

Числовой результат сохраняет полную точность внутри модели; интерфейс округляет Score до двух знаков. AI получает уже рассчитанные данные и не меняет числовые поля. Если модель недоступна, сервер явно сообщает об этом и предоставляет проверяемое объяснение из вычисленных фактов, не называя его ответом модели.

Для модельного объяснения настроены `NVIDIA_API_KEY` и `NVIDIA_MODEL`; NVIDIA имеет приоритет. `OPENAI_API_KEY` и `OPENAI_MODEL` остаются резервным вариантом. Модель выбирает только ID заранее рассчитанных фактов. `scripts/check-model.py` подтверждает настоящий модельный ответ одним контрольным вызовом без вывода ключа.

`GET /api/optimize` ищет максимум Score для исходных данных задачи и возвращает валидный расчёт вместе с `decisions`. Сервер повторно проверяет найденный набор через `simulate()`. Подсказка не меняет ручной сценарий до выбора пользователя; время первого запроса на текущем хосте около 4 секунд, результат кэшируется в процессе сервера.

`POST /api/recommend-change` принимает тот же `{"decisions":[...]}`, что и `/api/simulate`, и для корректного набора ищет лучшую допустимую замену не более одного решения. Возвращает `current` и `proposed` как полные результаты `simulate()`, `decisions` предложенного плана, `removed`, `added`, `score_delta`, `cost_delta` и `explanation`. Для невалидного набора возвращает HTTP 400 с причинами без Score. Предложенный набор повторно проверяется симулятором; модель получает оба готовых расчёта, но не меняет их. Интерфейс применяет замену только после нажатия пользователя.

## Контроль интеграции

1. Начальный Score: `52.55768`.
2. M7/Нура + M8/Нура + M10/Нура + M12/город + M5/Сарыарка: стоимость `95`, Score `56.54307`.
3. Невалидный набор возвращает причины без `score`.
4. Перестановка пяти решений не меняет результат.
5. README проверен по чистому запуску до финального push.

Интегратор переносит законченные изменения в `main` после проверки команды и тестов. Отдельный benchmark расширяет уверенность в оптимизаторе, но не подменяет контрольные случаи из датасета задачи.

Готовность ветки к передаче означает: владелец сообщил SHA commit, изменённые файлы, команды и наблюдаемые результаты проверок, а также ограничения. Саша сначала проверяет diff на выход за зону ветки, затем объединяет по одной законченной ветке и повторяет затронутый сценарий. Работа исследовательских агентов, включая graph patching и `gentle_precision`, не попадает в продукт автоматически: Саша принимает её только после сравнения с обязательным сценарием и воспроизводимым эталоном.
